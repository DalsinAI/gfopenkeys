# Where GFOS keeps secrets today (survey, 13 Nov 2026)

Dale asked on 13 Nov at 18:13 ("ensure we are not making a mess") for a list of every place GFOS apps keep secrets, and how each one keeps them, before gfopenkeys exists.

This page gives counts and mechanisms only. No secret value was opened or copied. It was taken from each repository's main branch on 13 Nov 2026 by reading the source.

## Summary

There are **12 places** where a GFOS program keeps or handles a secret:

| Kind | Count | Where |
|---|---|---|
| Kept on the Amiga, recoverable | 4 | gfopenmail, gfopenftp, FileZilla (gfamigafilezilla), gfopentelegram |
| Asked each time and never written | 4 | gfopenputty, GFAmigaRDP, GFOpenBrowser HTTP log-in, GFOpenBrowser proxy log-in |
| Kept on the host or card, never on the Amiga | 3 | network shares, Wi-Fi, gfopenremotedesktop |
| Session tokens | 1 | GFOpenBrowser cookies |

Today there are **four different ways of keeping a secret on the Amiga**:
- XOR obscuring (gfopenmail);
- AES-256-GCM under a key file kept beside it (gfopenftp);
- FileZilla's own (plain base64, unless its master password is set);
- plain text (gfopentelegram's API hash, gfopenmail's OAuth token file).

That is the mess Dale means. gfopenkeys replaces all four with one store.

## Each place

| # | Program | What it keeps | Where | How | Move to gfopenkeys? |
|---|---|---|---|---|---|
| 1 | **gfopenputty** (SSH, Telnet) | Nothing secret. Passwords and key passphrases are asked in the terminal each time. Host keys (public) go in `ENVARC:GFOpenPuTTY/HostKeys`, sessions (no secrets) in `ENVARC:GFOpenPuTTY/Sessions/`. `-pw` and `-pwfile` (from PuTTY's command line) take a password from the command line or a file the user names | `amiga/storage.c` | Not stored. HostKeys is PuTTY's sshhostkeys format | **First (Dale 18:13).** Add "remember in the keystore" to the password and passphrase prompts, and look the keystore up before asking. Host keys stay in HostKeys (public data, known_hosts form). There is no old secret store to import, so the migration test proves no secret is ever written to `ENVARC:GFOpenPuTTY/`, and that a session file carrying a `Password` line from another PuTTY fork is imported once and stripped |
| 2 | **gfopenmail** | One account: password, or the path to an OAuth2 token file | `ENVARC:GFOpenMail/Account`, the `secret =` line; the token file wherever the user put it | Password **XOR-obscured** and base64 (`o1:`). The source says "obscured, not encrypted: the Amiga has no key store". The token file is plain | Yes: `mail-imap/<host>/<user>` and `mail-smtp/<host>/<user>`, the token as `mail-oauth/<provider>/<user>`. Import once, then blank the `secret` line and delete the token file (with the user's yes) |
| 3 | **gfopenftp** | Site passwords, only when "Remember" is ticked | `ENVARC:GFOpenFTP/Sites` (`sealed v1:` per site), key in `ENVARC:GFOpenFTP/Key` | **AES-256-GCM** with the site's name and address as associated data, under a 32-byte machine key in the same drawer. The source says it doesn't protect anyone holding all of ENVARC: | Yes: `ftp/<host:port>/<user>` (and `ftps`, `sftp`). Import every sealed password, then empty `sealed` and delete `Key` |
| 4 | **FileZilla** (gfamigafilezilla, upstream 3.71) | Site Manager and recent-server passwords | `PROGDIR:Settings/` (`sitemanager.xml`, `recentservers.xml`), FileZilla's own format | Upstream FileZilla: **plain base64** unless the user sets FileZilla's master password; "Do not save passwords" turns it off | Later: a patch to FileZilla's login manager to use gfopenkeys (`ftp/<host:port>/<user>`, shared with gfopenftp), then strip the passwords from its XML. Until then the GFOS default is FileZilla's "Do not save passwords" |
| 5 | **gfopentelegram** | The Telegram API id and hash; the session (login) | `ENVARC:GFOpenTelegram/API` (`api_hash=` line); session data in TDLib's database on the host | API hash **plain text**. TDLib's database opens with an empty `database_encryption_key` | API hash: `telegram-api/my.telegram.org/<api_id>`. The TDLib session stays on the host, but its encryption key could come from gfopenkeys later (a host-side item) |
| 6 | **GFAmigaRDP** | Favourites hold host, user, domain and screen settings; **the password is never written** | `ENVARC:GFAmigaRDP/Favourites` | Asked each time; wiped from the field after use | Optional: "remember" for `rdp/<host:port>/<domain\user>` |
| 7 | **GFOpenBrowser**, HTTP log-in (401 Basic and Digest) | Kept for the browser session only (`CredentialPersistence::ForSession`) | Memory | Never written | Optional, later: "remember" as `http/<host:port>/<user>` with the realm in the label |
| 8 | **GFOpenBrowser**, proxy log-in | gfopencurl keeps proxy Basic and Digest, set from the browser's settings | The browser's settings | No password found written by today's browser source | When the proxy settings get a password field: `http-proxy/<host:port>/<user>` |
| 9 | **GFOpenBrowser**, cookies | Session cookies (log-in tokens for websites) | `PROGDIR:Cookies.db` (SQLite) | Plain, as browsers keep them | **No.** Cookies aren't credentials the user types. Encrypting the cookie jar is a browser item; noted here, not moved |
| 10 | **Network shares** (NETSHARES design, `host/net_shares.py`) | SMB user, domain, password | Host only: `/etc/amicradle/shares/<id>.cred` (root, 0600) on the card, `~/.config/amicradle/credentials/` (0600) on a PC. Write-only API; the Amiga never holds it | cifs credentials file | **No.** The host mounts the share, and the Amiga must never see the password. The Keys prefs list shares as "kept by the host" from `/api/shares` (`password: true|false`), with no value |
| 11 | **Wi-Fi** (card: `ac-pistorm network`, `ac-init`) | Network names and PSKs | Card only: `STATE/wifi-networks` (hex-coded) and `wpa_supplicant.conf`. Taken off the FAT boot partition once applied | wpa_supplicant's own | **No**, for the same reason as shares. Listed in the prefs as "kept by the card" |
| 12 | **gfopenremotedesktop** (host-side web remote) | The remote target's password; a random URL token per run | The PC: a mode-600 file (`--password-file`) or `$OPENREMOTE_PASSWORD`; the token in memory | Plain in a 0600 file | **No**: a Linux host program, outside the Amiga |

## Not swept yet

The wx ports (aMule's EC password in `amule.conf`, Poedit, Code::Blocks, KiCad) and the game ports haven't been swept. They are listed for the next survey pass, when each app moves.

None of them is in GFOS's base install.

## What it means for gfopenkeys

- **Four apps import** (mail, FTP, FileZilla, Telegram) **and two start remembering** (PuTTY, then RDP).
- **The browser's HTTP log-ins are optional.**
- **Host-held secrets** (shares, Wi-Fi, remote desktop) **stay on the host**. The prefs only show that they exist.
- **The naming rule** `service/host/user` covers every row (DESIGN.md section 3).
